# ba-key-AMAS 웹

스캐너(`../scanner`)가 만든 유저 데이터를 올려 두고, 계정 값으로 같은 선생님을 알아보는 Cloudflare Workers 앱이다. 스캐너 코드와는 폴더도 빌드도 따로다.

| 구성 | 선택 | 이유 |
|---|---|---|
| 런타임 | Workers + 정적 에셋 | 서버 관리가 없고, 서버 쪽 의존성은 0개다. 런타임 패키지가 없어 공급망 공격면이 작다 |
| DB | D1 (SQLite) | JSON 몇 개 분량이라 무료 한도 안이다. 학생 표를 SQL로 정렬 가능한 컬럼으로 둔다 |
| 화면 | 프레임워크 없는 HTML, CSS, JS | 의존성이 없고, `innerHTML`을 쓰지 않는다 |
| 개발 도구 | wrangler, typescript | `devDependencies`만, 정확한 버전으로 고정 |

## 회원코드와 계정

선생님은 게임의 회원코드(메뉴 모음 > 계정 > 고객센터 > 회원코드, 13자)로 알아본다. 닉네임은 표시용일 뿐이라 겹쳐도 된다(`닉네임#6자리` 키는 없어졌고, `#`도 닉네임에 쓸 수 있다).

**애드온에 알리는 말.** 애드온은 업로드할 때 회원코드를 한 번 묻고(화면에 보이지 않게, 두 번), 이 문구를 먼저 보여 준다. 이 웹의 메인 페이지(애드온 받기 옆)와 애드온 `--help`에도 같은 문구가 있다.

> 입력한 회원코드는 이 PC에서 변환(해시)된 값으로만 서버에 올라가며, 원본은 저장되거나 전송되지 않습니다. 서버는 그 값을 다시 비밀 값으로 변환해 저장합니다.

**값이 만들어지는 순서.**

1. 애드온(PC): 회원코드를 다듬는다. 앞뒤 공백을 자르고 영문 대문자와 숫자만 남긴다. 헷갈리는 글자는 `O`를 `0`으로, `I`와 소문자 `l`을 `1`로 접어, 잘못 친 한 글자가 계정을 둘로 쪼개지 않게 한다(두 코드가 정확히 그 자리에서만 다를 확률은 무시한다). 13자가 아니면 거절한다. 그다음 `account_id = hex(SHA-256("ba-key-amas/account/v1\0" + 코드))`를 만든다. 원본 코드는 저장, 전송, 로그, 출력 어디에도 가지 않고 `account_id`만 `%APPDATA%/baocr/upload.json`에 남는다. `--forget-account`가 그것을 지운다. 스크립트용으로 환경 변수 `BAOCR_MEMBER_CODE`를 받는다(명령줄 인자는 받지 않는다, 셸 기록에 남기 때문). 로컬 시험용 `BAOCR_ACCOUNT_ID_FOR_TESTING`은 `account_id`를 그대로 준다.
2. 서버: `account_hash = HMAC-SHA256(KEY_PEPPER, "account:" + account_id)`를 저장한다(UNIQUE). 비밀 값(pepper)이 있어서 데이터베이스만 새어도 회원코드를 대입해 볼 수 없다(코드 공간이 작아 pepper 없이는 전수 대입이 가능하다).
3. 주소와 순위에 쓰는 `public_id = HMAC-SHA256(KEY_PEPPER, "public:" + account_id)`의 앞 16자리(UNIQUE)가 따로 있다. 둘 다 코드를 되돌릴 수 없다.

같은 회원코드로 올리면 같은 줄을 갱신한다(닉네임 갱신, 학생과 진행 상태 교체, 공개 여부는 요청에 있을 때만 바꾼다). 새 회원코드면 새 줄이다. 새 계정은 비공개로 시작한다.

**접근.** 공개한 선생님은 순위와 검색에 나온다. 검색은 공개한 선생님의 닉네임 앞부분으로 하고, 같은 닉네임이 여럿이면 후보 목록(점수, 마지막 업로드)을 보여 준다. 비공개 선생님은 목록에도 검색에도 없고 `#/u/<public_id>` 주소로만 열린다. 이 주소는 추측할 수 없고 애드온이 업로드 뒤에 알려 준다. 공개 여부와 삭제는 애드온에서만 하며, `account_id`를 보내 증명한다. 틀린 `account_id`는 없는 계정(404)이다. 계정 값이 256비트 해시라서 닉네임 키 때와 달리 추측으로 잠글 일이 없어 잠금은 없다. IP당 분당 30건의 속도 제한(`LIMITER`)은 남아 있다.

### 위협 모델

- **회원코드는 업로드의 열쇠 구실을 한다.** 회원코드를 아는 사람은 누구나 그 계정으로 올려 데이터를 덮어쓸 수 있고, 공개 여부를 바꾸거나 지울 수 있다. 서버는 코드를 갖고 있지 않아 이를 막을 수 없다. 코드는 친구나 고객센터가 볼 수 있는 값이라 비밀 번호만큼 강하지 않다는 점을 알고 쓴다.
- **애드온 전용 헤더는 인증이 아니다.** `x-amas-*` 헤더는 누구나 보낼 수 있다. 브라우저의 우발적 요청, 옛 애드온, 실수를 막을 뿐이다.
- **저장 시 보호.** 데이터베이스에는 `account_hash`와 `public_id`만 있다. 둘 다 pepper 없이는 계산할 수 없어, 데이터베이스 유출만으로는 회원코드나 `account_id`를 추측할 수 없다.
- **pepper가 새면.** 코드 공간이 작아서 유출된 데이터베이스의 `account_hash`에 대해 회원코드를 대입해 계정을 알아낼 수 있게 된다(회원코드 13자 전수 대입은 비싸지만 불가능하지 않다). pepper를 바꾸면 모든 `account_hash`와 `public_id`가 달라져 기존 계정이 모두 끊기므로, 바꿀 때는 데이터를 지우고 다시 올리게 한다. 정해서 유지한다.
- **`account_id`가 새면.** `account_id`는 회원코드의 해시일 뿐이지만 업로드에는 그것만 있으면 된다. 가진 사람은 그 계정을 덮어쓰거나 지울 수 있다. 회원코드 자체는 알 수 없다(SHA-256의 역산이 필요하다). 코드 공간이 작아 `account_id`로 코드를 대입해 찾아내는 일은 가능하다. `account_id`는 요청 본문으로만 보내고(URL, 로그, Referer에 남지 않는다) 서버는 응답과 로그에 싣지 않는다. 사용자의 PC에서는 `upload.json`이 곧 열쇠이므로 남에게 주지 않는다.
- **계정 만들기는 막지 않는다.** 모르는 `account_id`로도 새 계정이 만들어진다(회원코드를 서버가 확인할 수 없다). 남용은 IP 속도 제한과 본문 크기 제한이 맡는다.
- 서버가 알 수 없는 것: 회원코드가 정말 그 사람의 것인지, 한 사람이 여러 계정을 만드는지.

## 화면

| 경로 | 내용 |
|---|---|
| `#/` | 메인 페이지. 리더보드와 그 위쪽의 검색창(검색창은 이 자리에만 있다). 리더보드는 두 탭이다. 학생 히트맵(공개한 선생님 전체의 캐릭터를 더한 지도, 학생 개별 스탯은 넣지 않음)과 선생님 순위. 순위에서 선생님을 누르면 그 선생님의 상세 화면으로 간다 |
| `#/u/<public_id>` | 선생님의 상세 화면. 순위, 검색 결과, 애드온이 알려 준 주소로 열린다. 비공개 선생님도 이 주소로 열린다. 탭은 오버뷰(기본, 학생 히트맵), 학생(썸네일), 학생 리스트, 스토리, 이벤트 스토리, 임무, 모모톡, 당번 · 메모리얼, 스케줄 |

검색창은 공개한 선생님의 닉네임 앞부분으로 찾는다(대소문자와 전각은 같게 본다). 한 명이면 바로 열고, 여럿이면 후보 목록을 보여 준다. 웹에는 공개 전환과 삭제가 없다. 이것들은 애드온에서만 한다(아래).

업로드 화면도 없다. 데이터는 애드온에서만 올린다.

## 업로드와 버전

```
ba-key-AMAS --upload https://<서버> [--public] [--nickname 이름]
```

```
ba-key-AMAS --manage https://<서버> --visibility public|private
ba-key-AMAS --forget-account
```

공개 여부도 애드온에서만 바꾼다. `--public`이 없으면 서버가 가진 공개 여부를 그대로 둔다(새 계정은 비공개).

마지막 학생 스캔(`students.json`)과 진행 스캔(`latest.json`)을 보낸다. 닉네임은 진행 스캔이 읽은 계정 이름이다. 처음 올릴 때 회원코드를 묻고(위 "회원코드와 계정"), 이후에는 저장된 `account_id`로 같은 줄을 갱신한다. 업로드가 끝나면 그 선생님의 주소(`<서버>/#/u/<public_id>`)를 보여 준다. `account_id`가 새어 나가지 않도록 https와 loopback 주소만 받는다.

버전은 `src/version.ts`가 관리한다. 서버가 받아들이는 범위를 정한다.

- 업로드 규약 2부터 `account_id`로 계정을 알아본다. 규약 1(닉네임과 키)의 애드온은 426과 설치 링크를 받는다.
- 애드온은 `x-amas-protocol`(업로드 규약 번호)과 `x-amas-addon`(애드온 버전) 헤더를 보낸다. 서버는 `MIN_PROTOCOL`부터 `PROTOCOL`까지를 받는다. 범위 밖이면 426이고, 응답에 설치 안내 링크(`download`)가 들어 있다.
- 스캔 파일의 `schema_version`도 본다. 학생 명단이 `MIN_ROSTER_SCHEMA`, 진행 상태가 `MIN_PROGRESS_SCHEMA`보다 낮으면 426이다.
- 서버를 고쳐 스키마가 바뀌거나, 새 애드온의 데이터를 받아야 할 때 `MIN_PROTOCOL`을 올려 구버전을 거부한다. 하위 호환이 되는 변경이면 범위를 그대로 둔다.
- 브라우저의 요청(`Origin`, `Sec-Fetch-*` 헤더)은 403이다. 이 검사는 애드온을 식별할 뿐 인증하지는 않는다. 헤더는 누구나 보낼 수 있다.
- 설치 링크는 `wrangler.jsonc`의 `ADDON_URL`이다. 지금은 GitHub 릴리즈 페이지를 가리키며, 주소가 정해지면 그 값만 바꾼다. `GET /api/version`이 서버 버전과 범위, 링크를 돌려준다.

## API

`GET`을 빼고는 모두 `POST`, `Content-Type: application/json`, 본문 3 MB 이하다.

| 경로 | 본문 | 응답 |
|---|---|---|
| `/api/upload` | `{account_id, nickname, public?, roster, progress?}` (애드온 헤더 필요) | 새 계정이면 201, 있으면 200(갱신). `{created, public_id, students, public, score}`. `public`을 보내지 않으면 공개 여부를 그대로 둔다 |
| `/api/visibility` | `{account_id, public}` (애드온 헤더 필요) | 리더보드 공개 여부 변경. 없는 계정이면 404 |
| `/api/delete` | `{account_id}` (애드온 헤더 필요) | 삭제. 없는 계정이면 404 |
| `GET /api/search?q=` | 없음 | 공개한 선생님 중 닉네임이 `q`로 시작하는 사람 20명까지 `{matches: [{public_id, nickname, score, updated_at}]}` |
| `GET /api/public?id=` | 없음 | `public_id`의 선생님 정보(크레딧과 AP 제외). 비공개 선생님도 열린다. 없으면 404 |
| `GET /api/leaderboard/students` | 없음 | 공개한 선생님 전체의 캐릭터를 의상을 합쳐 더한 목록(캐릭터, 점수 합, 보유 인원, 의상). 학생 개별 스탯은 담지 않음 |
| `GET /api/leaderboard` | 없음 | 공개 유저 100명까지, 점수 순, `public_id` 포함. 60초 캐시 |
| `GET /api/version` | 없음 | 서버 버전, 받는 업로드 규약 범위, 설치 링크 |

`roster`는 스캐너의 `students.json` 그대로다. 서버가 알려진 필드만 범위를 검사해서 남기고 나머지는 버린다. 메모리얼 로비 해금은 `progress.duty.students`의 이름과 학생 이름을 맞춰 가져온다.

## 에셋

게임 이미지는 저장소에 없고 `npm run assets`가 빌드 때 받아 온다. 모두 `.gitignore` 대상이다.

| 스크립트 | 만드는 것 | 출처 |
|---|---|---|
| `extract-assets.py` | 학생 카탈로그, 초상화, 아이콘, 전신 입상, 메모리얼 로비, 학교 로고, `meta.json` | SchaleDB(글로벌 출시 학생만) |
| `extract-halos.py` | 학생별 헤일로 `public/halos/<id>.png` | 블루 아카이브 위키 `HALO一覧` 페이지. 일본어 이름을 SchaleDB의 일본어 이름과 맞춘다. 의상은 기본 캐릭터의 헤일로를 쓴다 |
| `extract-lobby.py` | 고화질 메모리얼 로비 `public/card-lobby/<id>.webp`(760x1280)와 목록 `card-lobby.json` | 블루 아카이브 위키(bluearchive.wiki)의 `Memorial_Lobby_<이름>` 파일. 위키 API로 목록을 받고 SchaleDB 영어 이름과 맞춘 뒤, 얼굴 기준으로 카드 세로 모양으로 자른다. 원본은 `scripts/.cache`에 둔다 |
| `crop-art.py` | 카드 그림 `public/card/`(6:5), `public/card-lobby/`(위키에 없는 학생의 SchaleDB 썸네일 대체분), 얼굴 위치 `faces.json` | 입상의 투명 영역으로 인물 위치를 찾아 얼굴 쪽을 인물 폭에 맞게 자르고, 학생마다 같은 크기로 맞춘다. 게임의 초상화 전용 이미지(머리 크롭)는 카드에 쓰지 않는다. 학생 타일, 히트맵, 작은 아이콘은 그 이미지를 그대로 쓴다 |

위키에 `npm run assets`는 마지막에 `audit-assets.py`를 돌린다. 학생마다 초상화, 아이콘, 전신 입상, 카드 크롭, 로비, 얼굴 위치, 헤일로, 학교 로고, 슬롯 종류가 있고 이미지가 실제로 열리는지(오류 페이지를 이미지로 저장하지 않았는지) 확인하며, 빠진 것이 있으면 빌드를 멈춘다. 원본에 없는 것(사텐 루이코의 학교 로고)만 `KNOWN_GAPS`에 적어 둔다. 직접 보려면 `npm run audit`.

학생 카탈로그(`src/catalog.json`)는 이름이 아니라 학생 ID가 키다. "호시노(무장)"은 탱커 모드와 딜러 모드가 있는 한 학생인데 게임은 모드마다 따로 기록해서 ID가 둘이다. 선생님의 명단에서는 한 학생(이름 하나, 한 줄)이고, 스캐너가 화면에서 찾은 ID(`reference.id`)가 어느 모드의 그림과 슬롯을 쓸지만 정한다. ID 없는 옛 업로드는 이름의 첫 항목을 쓴다.

위키에 메모리얼 로비 이미지가 없는 학생은 SchaleDB의 182x144 썸네일을 쓰므로 키우면 다소 흐리다. 카드 배경은 SchaleDB의 수집 화면 배경(`public/backgrounds/`)이다. 헤일로는 위키에 없는 학생(약 13명)이 있고, 그 학생은 헤일로 없이 나온다. 위키 페이지에는 이용 조건 표기가 없었으므로, 이미지는 배포 저장소에 넣지 않고 빌드 때만 받는다.

## 학생 카드

카드의 그림(일반, RR, AR)은 학생에게 업로드 때 정해진 배경을 깔고 그 위에 입상의 얼굴 쪽을 얹는다. 학생 타일은 게임의 초상화 전용 이미지를 그대로 쓴다. 카드는 380x640 한 크기로 그려서 창에 맞춰 통째로 줄이므로 창이 달라져도 표현이 같고, 축척은 학생과 무관하다(의상 선택줄이 있어도 같다). "고정"은 글자 대신 핀 아이콘이며, 마우스를 올리면 글자가 나온다.

카드의 기본 색과 무늬는 공격 타입이 정하고(폭발 붉은색, 관통 호박색, 신비 푸른색, 진동 보라색, 분해 초록색), 방어 타입이 띠의 보조 색을 정한다. 역할, 포지션, 타입은 아이콘이며 마우스를 올리거나 포커스를 주면 글자가 나온다. 공격과 방어 타입은 하나의 알약으로 합쳐 (신비 / 중장갑) 식으로 보인다. 등급(SAR 등)과 전체 순위는 카드 맨 아래 줄에 있다. 등급은 게임의 전체 캐릭터 수(의상을 합친 수, 빌드 때 `meta.json`의 `character_count`) 대비 비율로 정한다. 위에서부터 SAR 1%, UR 2%, SR 3%, AR 6%, RR 10%이고 `detail.js`의 `GRADE_SHARE`에서 바꾼다. 같은 비율이어서 캐릭터가 적은 선생님과 많은 선생님의 등급이 같은 뜻이다.

일반, RR, AR 카드는 배경 위에 입상을 올려 만든다. 배경은 학생을 처음 올릴 때 서버가 무작위로 하나 고르고, 그 배경을 크게 키워 좌, 중, 우 세 구간 중 하나를 보여 준다. 고른 값은 학생별로 저장해 다시 올려도 바뀌지 않는다. 카드 색은 어둡고 차분하게, 호일은 일러스트 안에서만 옅게 보이도록 했다.

학생을 누르면 카드가 열린다. 입장 연출은 헤일로가 돌며 반짝이다가 카드로 바뀌는 순서이고, 카드는 포인터를 따라 기울고 광택이 움직인다. 전체 점수 순위로 등급이 정해진다. 1~3위는 일러스트가 카드 전체를 차지하고 글자가 그 위에 얹힌다. 1위 SAR은 프레임이 없고 무지개 호일, 2위 UR은 금빛 프레임과 금색 호일, 3위 SR은 은빛 가는 프레임과 결 무늬 호일이다. 4위 AR은 프레임 카드에 줄무늬 호일, 5위 RR은 프레임 카드에 호일, 나머지는 일반 카드다. 같은 학생의 의상이 여러 벌이면 카드 아래의 의상 선택줄로 골라 볼 수 있다. 광택은 일러스트 안에서만 움직이고 세기를 낮춰, 글자를 가리거나 눈을 부시게 하지 않는다. 카드는 한 크기로 그린 뒤 창 크기에 맞춰 줄여 보여 주며, 이미지가 없으면 잘라 둔 일러스트, 원본, 작은 초상화 순으로 대신한다. 카드 뒷면에는 스캔한 모든 능력치(전투 능력치, 상세 능력치, 지형 적응, 장비, 신비 해방)가 있다. 정밀 스캔을 하지 않은 학생은 뒷면이 비어 있다.

## 히트맵

의상이 여럿인 학생은 한 칸을 좌, 중, 우 조각으로 나누고 조각마다 그 의상의 카드를 연다. 조각 수는 칸 폭을 조각 최소 폭(50px)으로 나눈 값이다(최대 3). 의상이 하나 늘 때마다 칸 면적에 45%의 보너스를 주어 조각이 고를 만한 크기가 되게 한다(`OUTFIT_ROOM`, 배치에만 쓰이고 점수에는 영향이 없다). 조각에 마우스를 올리면 그 조각 전체가 위로 떠올라 이웃 칸 위로 튀어나오고 테두리가 켜지며 옆 조각은 조금 어두워진다. 안쪽 그림을 확대하지는 않는다. 타일, 즐겨찾기, 모모톡도 호버하면 그 면이 떠오른다. 선생님 상세에서만 카드가 열리고, 리더보드의 합산 히트맵에는 개인 카드가 없어 조각을 고르지 않는다.

칸의 넓이가 점수다. 작은 칸에도 얼굴이 보이도록 모든 초상화의 얼굴 중심(`faces.json`, 빌드 때 `crop-art.py`가 얼굴 검출로 만든다)을 두고, 칸의 모양에 맞춰 그림의 크기와 위치를 정한다. 가로로 긴 칸과 세로로 긴 칸 모두 얼굴이 가로 가운데, 세로는 위에서 약 3분의 1에 오고, 세로로 긴 칸은 그림을 조금 키워 얼굴을 위로 올릴 여지를 만든다. 얼굴을 찾지 못한 학생은 전체의 평균 위치를 쓴다. 호버는 테두리만 강조하고 그림을 밝게 하지 않는다.

창 크기에 따라 갈라지지 않도록 지도 높이는 학생 한 명이 최소 3800 px² 정도를 받게 정한다(`heatmap.js`의 `CELL_AREA`). 좁은 창은 지도가 더 길어지고 스크롤된다. 1920×1080, 1366×768, 1024×600, 800×1100, 480×860, 2560×900에서 85칸 중 77칸 이상(최대 84칸)에 초상화가 들어가고, 얼굴 위치의 평균은 칸의 가로 0.51, 세로 0.36 부근으로 같다.

## 장비

스캔은 슬롯의 티어와 레벨, 장착 여부만 읽는다. 아이템 이름과 슬롯의 종류(모자, 장갑 등), 티어별 최대 레벨은 정적 데이터(SchaleDB의 장비 표, 빌드 때 `meta.json`과 `catalog.json`에 들어간다)에서 (종류, 티어)로 찾는다. 종류와 티어마다 아이템은 하나뿐이다. 스캐너의 같은 표는 `wikidb`의 `equipment_item`, `student_equipment_slot`이다.

## 점수

리더보드 점수는 업로드할 때 `src/score.ts`가 계산해 저장한다. 산정 기준은 화면과 API 응답에 싣지 않는다. 응답에는 합계만 있고 항목별 점수는 없다. 기준을 바꾸면 `SCORE_VERSION`을 올리고 유저가 다시 올려야 새 기준이 적용된다.

## 보안 설정

- 화면과 에셋은 `public/_headers`의 CSP(`default-src 'none'`, 스크립트와 스타일은 `'self'`만), `X-Frame-Options`, `nosniff`, `no-referrer`가 붙는다. API 응답은 `Cache-Control: no-store`다.
- `account_id`와 회원코드는 URL, 응답, 로그에 나오지 않는다(`test/accounts.test.ts`가 확인한다).
- 상태를 바꾸는 요청은 Origin이 다르면 거부하고, JSON이 아니면 거부한다(CSRF). 쿠키는 쓰지 않는다.
- SQL은 모두 바인딩 인자로 쓴다.

## 개발

```

npm run assets          # 학생 카탈로그와 초상화를 SchaleDB에서 받는다 (커밋하지 않는다)
echo KEY_PEPPER=dev-only > .dev.vars
npm run db:local
npm run dev
ba-key-AMAS --upload http://127.0.0.1:8787 --public   # 처음에는 회원코드를 묻는다
npm test ; npm run typecheck

```

## Cloudflare 깃 연결 배포

1. `npx wrangler d1 create ba-key-amas`를 한 번 실행하고 나온 ID를 `wrangler.jsonc`의 `database_id`에 넣는다.
2. 대시보드에서 Workers Builds로 이 저장소를 연결하고 Root directory를 `web`으로 한다.
3. Build command는 `npm ci && npm run assets`, Deploy command는 `npx wrangler d1 migrations apply ba-key-amas --remote && npx wrangler deploy`로 한다. 마이그레이션은 자동으로 돌지 않아서 배포 명령에 넣었다.
4. 비밀값 `KEY_PEPPER`는 대시보드의 Variables and secrets에 Secret으로 넣는다(32바이트 이상의 무작위 값). 바꾸면 기존 계정이 모두 끊기므로 한 번 정하고 유지한다. 새어 나가면 위 위협 모델을 본다.
   마이그레이션 `0007`은 사용자 표를 새로 만들며 이전 모양의 행을 지운다(배포 전 시험 행만 있다는 전제). 데이터가 쌓인 뒤에는 이런 마이그레이션을 쓰지 않는다.
5. 초상화와 `src/catalog.json`은 저장소에 없고 빌드 때 만든다. 게임 이미지를 저장소에 두지 않기 위해서다.

## 카드 돌리기

카드를 끌면 끈 만큼 그 방향으로 돈다(좌에서 우, 우에서 좌). 위아래로 끄는 부분은 카드를 기울이므로 대각선으로 끌어도 된다. 놓았을 때 55도를 넘었으면 끌던 방향으로 끝까지 돌아 반대 면을 보여 주고, 못 넘었으면 제자리로 돌아온다. 뒤집기 버튼은 없다. 카드의 앞면과 뒷면 어디든 끌거나 누르면 뒤집힌다(의상 선택줄과 칩 위는 제외). 그림은 브라우저의 끌어다 놓기가 걸리지 않게 막아 두었다. `FLIP_AT`, `PX_TO_DEG`, `TILT_MAX`는 `public/detail.js`의 `dragFlip`에 있다.

## 카드 뒷면

뒷면은 앞면과 같은 크기이고 스크롤이 없다. 기본으로 전투 능력치, 경험치, 지형 적응, 장비를 보여 주고, 전투 능력치 영역에 마우스를 올리면 상세 능력치와 신비 해방이 카드 안에 팝업으로 뜬다(CSS의 `:has`로 처리하며 스크립트는 없다).

## 아이콘

프로젝트 아이콘은 `public/brand/icon-{512,192,64,32}.png`이고 헤더 로고, 파비콘, 홈 화면 아이콘으로 쓴다. 같은 그림의 `scanner/assets/ba-key-amas.ico`(16~256)는 `scanner/crates/cli/build.rs`가 Windows 빌드의 `ba-key-AMAS.exe`에 넣는다(`winresource`). 원본 그림을 바꾸면 두 곳을 함께 다시 만든다.
