# 애드온 그리기와 반응 성능 점검

2026-11-25에 오버레이의 그리기 방식, 렌더링 비용, 깜박임 요인, 반응 속도를 점검했다. 게임이 꺼져 있는 상태에서 잰 값과 게임 없이 도는 측정 도구(`render_bench`, `perf_loop`)의 값이다. 게임이 떠 있는 동안의 값은 재지 못했다(아래 "확인하지 못한 것").

## 그리기 방식

- 오버레이는 레이어드 윈도우 4개다(메인 카드, 인게임 카드, 초상화 아이콘, 툴팁). 모두 `UpdateLayeredWindow`로 픽셀 단위 알파 비트맵을 통째로 넘긴다. 그리기 결과가 같으면(`key`) 다시 넘기지 않는다. 그래서 가만히 있을 때는 그리지 않는다.
- 카드와 아이콘은 CPU에서 한 장의 RGBA 이미지로 그린 뒤 BGRA로 바꿔 윈도우에 넘긴다. GPU를 쓰지 않는다.
- 오버레이 스레드는 50ms마다 마우스, 게임 창 위치, 들어온 클릭을 본다. 상태가 바뀌면 `Wake`로 바로 깨어난다.

## 측정

| 항목 | 전 | 후 |
|---|---|---|
| 게임을 기다리는 동안 애드온 CPU | 한 코어의 10.8% | 0.05% |
| 초상화 아이콘 24개 그리기, 게임 1601x1201 | 약 20 ms | 약 5.6 ms |
| 같은 것, 게임 2560x1920 | 약 49 ms | 약 12.6 ms |
| 오버레이 스레드, 카드가 그대로일 때 | 0.0% | 0.0% |
| 오버레이 한 번 살피는 비용 | 0.14 ms | 같음 |
| 메인 카드 그리기(11줄), 폭 360 px | 약 3.9 ms | 같음 |

## 찾아서 고친 문제

1. **게임이 없을 때 1초마다 데스크톱 전체를 캡처한다.** 게임 창을 찾으려고 `detect_region`이 매번 화면 전체의 스크린샷을 찍었다(약 100 ms). 필요한 것은 프레임 크기뿐이고 이는 데스크톱 크기에서 계산된다. 게임이 떠 있는 동안에도 25번에 한 번씩 같은 일을 했다. 이제 HCU가 마지막에 본 프레임 크기와 같으면 스크린샷을 건너뛴다(`hcu/src/window.rs`).
2. **아이콘 레이어가 게임 화면 전체 크기다.** 아이콘은 일부분에만 있는데 비트맵을 전체 크기로 만들고, 지우고, 윈도우에 넘기고, 합성기가 전부 블렌딩했다. 이제 아이콘이 닿는 영역만 그리고 그 위치에 창을 둔다(`render_marks_clipped`). 24개 격자에서 면적이 25%다.
3. **초상화 테두리를 상자 전체를 훑어 그렸다.** 테두리는 두께가 몇 픽셀인 고리인데 4겹을 상자의 모든 픽셀에서 거리를 계산했다. 이제 가장자리 근처 픽셀만 본다. 결과 픽셀은 전부 훑는 방식과 같다(테스트가 비교).
4. **같은 테두리와 같은 아이콘을 카드마다 다시 그렸다.** 격자의 테두리는 크기와 등급이 모두 같고, 아이콘도 같은 등급과 같은 타입이 반복된다. 종류마다 한 번 그려 복사한다. 복사는 가장 가까운 정수 픽셀에 놓으므로 반 픽셀 안에서 다르다.
5. **레이어를 넘길 때 픽셀마다 나눗셈 세 번.** 대부분의 픽셀은 완전 투명이거나 불투명이라 곱하고 나눌 필요가 없다. 이 두 경우는 그대로 복사한다(결과 바이트는 같다는 테스트가 있다).
6. **마우스와 클릭을 90 ms마다 본다.** 클릭은 다음 살피는 때까지 기다려서 평균 45 ms가 걸렸다. 50 ms로 줄여 평균 25 ms가 되고, 비용은 한 코어의 0.3%다.

## 깜박임

- `UpdateLayeredWindow`가 한 번에 바꾸므로 그리는 도중의 반쯤 그려진 화면은 보이지 않는다.
- 아이콘이 잠깐 사라지는 것은 설계다. 화면이 움직이는 동안 옛 화면의 아이콘이 엉뚱한 곳에 있지 않도록 내린다(`transition`). 앞서 고친 빠른 편성 진입 직후 사라지는 문제는 이 내림이 잘못 불리던 것이었다.
- 다른 창이 게임을 가리면 모든 레이어를 숨겼다가 다시 보일 때 처음부터 다시 그린다. 이 동작에서 깜박임이 날 수 있지만 재현하지 못했다.

## 게임이 떠 있을 때 (실제 측정)

같은 정지 화면(전투 종료 화면)에서 30초 동안의 CPU. 기존 루프는 변화가 있는지 보려고 프레임 전체를 캡처했고(한 번에 약 105 ms), 아이콘이 떠 있는 동안(빠른 편성)은 20 ms만 쉬어서 한 코어를 거의 다 썼다. 새 루프는 64x48 크기의 프로브(약 19 ms)로 읽어 둔 화면과 같은지만 보고, 다르면 예전처럼 전체 캡처로 읽는다.

| 루프 | CPU (한 코어 대비) |
|---|---|
| 프레임 전체 캡처로 확인(`BAOCR_PROBE=0`) | 25.2% |
| 프로브로 확인(기본) | 4.6% |

- 프로브의 임계값은 1.2다. 정지한 화면의 프로브 사이 거리는 0.2에서 0.6이었고, 화면이 바뀌면 1.5에서 수백이었다(`probe_lab`로 측정, 게임 대기 화면과 이동 중 화면).
- 빠른 편성의 틀린 점: 전체 캡처 방식은 아이콘이 떠 있는 동안 캡처와 20 ms 휴식만 반복해서 계산상 한 코어의 약 84%였다. 프로브 방식은 프로브와 70 ms 휴식이라 약 21%다(계산값, 아직 라이브로 재지 못했다).
- 전투 중에는 전체 캡처로 전투 종료를 감시하므로 이 경로를 쓰지 않는다. 이 부분은 400 ms마다 캡처해서 한 코어의 약 21%다.

## 빠른 편성에서 (실제 측정, 2026-11-25)

아이콘이 떠 있는 빠른 편성 화면에서 30초 동안의 애드온 CPU는 한 코어의 **8.5%**다. 이전 루프는 캡처와 20 ms 휴식만 반복해서 한 코어의 약 84%였다(계산값). 그 사이 중간 단계로 15.6%를 측정했는데, 남은 7%는 아래 버그였다.

- **매 루프 카드를 처음부터 다시 계산하던 버그.** `Assistant::tick`이 "스캔한 지 N분" 글자가 바뀌었는지 `age_shown`과 비교했는데, `age_shown`을 아무 데서도 갱신하지 않아 언제나 "바뀐" 것으로 보고 `present()`(모든 위젯과 임무 판정을 다시 계산)를 매 루프 불렀다. 빠른 편성에서 루프당 13 ms였다. 이제 글자가 실제로 바뀔 때만 계산한다(`poll`이 13 ms에서 0.0 ms로).
- **빈 슬롯.** 학생을 뺀 슬롯은 게임이 회색 EMPTY 판을 그린다. 초상화 상관도는 이 평평한 판에도 어떤 학생 템플릿을 높은 점수로 맞췄다(호시노로 읽힘). 가운데 44 px의 색 퍼짐과 밝기 퍼짐으로 빈 슬롯을 먼저 가려 낸다(빈 판 8 / 12, 초상화는 12.6 / 23.6 이상). 빈 슬롯은 이름 순서 채우기에서도 건너뛴다.

### 스쿼드에 넣고 뺄 때

옆 학생을 클릭해 4번째 스트라이커를 빼고 다시 넣어 보고(각 3번), 클릭부터 애드온이 새 편성을 낼 때까지 쟀다.

| 단계 | 걸린 시간 |
|---|---|
| 처음 | 1.1~1.4 s (프레임 전체 OCR 약 700 ms를 두 번까지) |
| 격자가 그대로면 글자 읽기를 건너뜀 | 0.4~0.9 s |
| 새 격자는 두 번 연달아 같을 때 읽음 | 0.4~0.9 s (클릭이 화면을 흔드는 순간을 읽지 않음) |

- 격자가 그대로라는 판정은 카드마다 위치와 이름표 지문(이름표를 잉크로 바꾼 바이트의 해시, 썸네일 보기에서는 그림의 거친 평균)으로 한다. 최근 세 격자를 기억한다. 클릭이 화면을 잠깐 흔들면 그 순간이 다른 격자로 읽히고, 곧 이어 흔들리기 전 격자가 돌아오기 때문이다.
- 이 화면의 선택 상태(초록 테두리)와 스쿼드 슬롯은 픽셀로 다시 읽는다. 프로브 방식도 이 작은 변화를 놓치지 않았다(프로브 끈 쪽과 시간이 같았다).

### 스크롤할 때

격자를 두 칸 내리고 올려, 스크롤을 시작한 시각부터 새 카드 목록이 나올 때까지 쟀다. 1.5~2.0 s. 게임 자체의 스크롤 감속이 약 0.7 s이고, 나머지는 새 격자 확인 한 번(약 0.13 s), 격자 부분만 읽는 텍스트 인식(약 0.34 s), 카드 읽기(약 0.16 s)다. STRIKER 탭에서는 격자 부분(프레임의 약 20%)만 글자로 읽는다. 기록된 7개 프레임 모두에서 전체 프레임을 읽은 것과 카드가 같았다(`extract/tests/cards.rs`). 전체 프레임을 읽는 것에 비해 약 0.3 s 줄었다. SPECIAL 탭은 스페셜 이름을 팝업 아래에서 읽어야 해서 전체 프레임을 읽는다.

## 남은 요인과 제안

- **스크롤 반응.** 게임의 감속이 끝나야 읽는다. 감속 중에 카드를 읽는 방법은 위치가 계속 바뀌어 맞지 않는다. 읽는 쪽에서는 이름표 지문으로 이미 읽은 카드의 이름을 다시 쓰는 방법(스크롤로 반쯤은 같은 카드)이 남아 있다.
- **전투 중의 폴링.** 전투 종료를 알아채려고 400 ms마다 전체 캡처를 한다(한 코어의 약 21%). 전투 HUD의 몇 군데만 작게 잡으면 줄일 수 있다.
- **초상화 아이콘의 글자 그리기.** 아이콘 안의 글자는 매번 글리프 외곽선에서 그린다. 아이콘을 복사하게 되어 거의 보이지 않는 비용이 됐다.
- **카드 폭이 640 px일 때 약 12 ms.** 해상도가 큰 화면에서 카드를 다시 그릴 때만 해당하고, 카드는 상태가 바뀔 때만 그린다.

## 확인하지 못한 것

- 게임이 떠 있는 동안의 CPU와 프레임 영향. 측정할 때 게임이 꺼져 있었다. 위 표의 "게임을 기다리는 동안"만 실제 프로세스로 잰 값이다.
- 아이콘 복사의 반 픽셀 이동이 화면에서 눈에 띄는지.
- 레이어를 넘기는 시간(`UpdateLayeredWindow`)의 변화. 아이콘 레이어가 4분의 1 면적이 되었으므로 줄었을 것으로 추정하지만 재지 않았다.

측정 도구: `cargo run -p baocr-overlay --release --example render_bench`, `OVERLAY=20 cargo run -p baocr --release --example perf_loop`, 실제 실행 중에는 `BAOCR_PROFILE=1`.

## 반응 속도 힐클라임

목표는 게임에서 입력한 뒤 애드온이 새 상태를 내기까지의 시간을 1초 안쪽으로 줄이는 것이다. 라이브 측정 틀은 `scripts/overlay-latency.py`(클릭과 스크롤을 6번씩, 중앙값)이고 `BAOCR_TRACE=1`로 한 번의 반응에서 시간이 가는 곳을 본다. 시도와 결과는 `decision.tsv`(저장소 밖)에 적었다.

| 동작 | 시작 | 지금 (중앙값) | 게임 자체의 응답 |
|---|---|---|---|
| 스쿼드에서 빼기 | 843 ms | 429 ms | 약 220 ms |
| 스쿼드에 넣기 | 995 ms | 462 ms | 약 220 ms |
| 격자 아래로 스크롤 | 1780 ms | 939 ms | 화면이 멈추기까지 약 710 ms |
| 격자 위로 스크롤 | 1612 ms | 1079 ms | 화면이 멈추기까지 약 700 ms |

유지한 것:
- 라벨이 거의 멈추면 읽기(스크롤의 끝자락 몇 픽셀은 수백 ms 이어진다).
- 클릭으로 포인터 아래 카드가 밝아져도 같은 격자로 보기(라벨의 4분의 1까지).
- 격자 지문을 한 바퀴에 한 번만 계산하기.
- 이미 읽은 라벨은 이름을 기억하고 새 라벨의 띠만 글자 인식하기.
- 슬롯 그림이 그대로면 슬롯 인식을 건너뛰기.
- 팝업 안의 화면을 HCU 대신 화면에서 바로 읽기(한 번에 95 ms에서 33 ms. 같은 화면에서 카드 이름이 같음을 `examples/grab_cmp.rs`로 비교).

되돌린 것: 슬롯 그림 16단계 지문(같은 화면의 두 기록에서도 달랐다).

남은 몫은 게임의 감속(스크롤)과 응답(클릭)이 대부분이다. 스크롤에서 애드온이 더하는 시간은 약 230 ~ 390 ms다.
