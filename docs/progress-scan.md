# 진행 상태 스캔과 영수증 내보내기

학생 스캔 말고도 계정 전체의 진행 상태를 모아 두는 스캔을 추가한다. 모은 값은 [BAReceipt](https://subba0987.github.io/BAReceipt/)가 받는 백업 파일로 내보낸다. BAReceipt는 지금 모든 값을 손으로 입력하는 정적 페이지이고, 이 기능은 그 입력을 자동으로 채우려는 것이다.

이 문서는 계획과 조사 결과를 적는다. 구현한 항목은 표의 상태 열에서 구분한다.

## 스캔할 값

2026-11-24에 16:9 창 모드의 실제 게임에서 각 값이 있는 화면을 조사했다. 기록은 `fixtures/screens/w169-*.boxes.txt`(OCR 글자 상자)와 일부 PNG에 있다.

| 값 | 출처 화면과 읽는 법 | BAReceipt 키 | 상태 |
|---|---|---|---|
| 선생님 이름, 레벨 | 로비 왼쪽 위. 글자로 읽힌다("소다팝", "69"). 계정 화면(메뉴 모음, 계정)은 아직 보지 않았다 | `basic["in-nick"]`, `basic["in-level"]` | 스캔 구현(로비), 4:3 확인 |
| 가입 서클 | 소셜 메뉴의 서클. 아직 보지 않았다 | `basic["in-circle"]` | 조사 필요 |
| 스케줄 지역 레벨 | 스케줄 화면의 `Location Select`. 지역마다 `RANK n 지역명` 한 줄이고 `지역 랭크 총합 RANK 56`이 있다. 목록이 스크롤된다 | 영수증 본문 | 스캔 구현, 4:3 확인(11개 지역, 합 56) |

| 메인 스토리 진행 | 스토리, 1부 메인 스토리. 편마다 `클리어` 표시가 있고, 장 화면에 `모든 에피소드를 클리어 했습니다.` 문구와 `complete!` 도장이 있다 | `main` (`ms_n_ch`, `ms_n_ep`) | 읽는 함수와 내보내기 구현(`story`) |

| 이벤트 스토리 진행 | 이벤트 일람의 `이벤트 스토리` 탭. 지난 이벤트가 시간순 격자로 늘 열려 있고, 완료한 이벤트에 도장이 찍힌다. 이벤트 이름이 그림 로고라 글자로 읽을 수 없으므로 격자의 순서로 `eventStoryList`와 맞춘다 | `event` | 스캔 구현, 4:3 확인(30칸, 도장 25개) |

| 모모톡의 인연 랭크 | 모모톡 학생 목록. 줄마다 학생 이름과 하트 안의 숫자가 있다 | 내보내기 대상 아님 | 읽는 함수 구현(`momotalk`), 숫자는 하트를 잘라낸 그림에서 읽는다 |
| 모모톡 에피소드 진행 | 학생의 인연 스토리. 학생별로 들어가야 하며 아직 보지 않았다 | `students[].momotalk` | 조사 필요 |
| 학생 레벨, 성급, 스킬 | 학생 스캔 결과 | `students` | 학생 스캔에 있음 |

화면 조사에서 알게 된 점은 다음과 같다.

* 이 화면들에는 눌러서 보상을 받거나 전투로 들어가는 버튼이 가까이 있다(이벤트 정보의 `보상 받기`, 스토리의 `입장`). 스캔은 누를 위치를 글자 상자로 찾고, 허용한 라벨(탭 이름, 화살표, 닫기)만 누른다.
* 스토리의 장을 누르면 `...로 이동하시겠습니까?` 확인 팝업이 뜰 수 있다. 취소를 눌러 닫고 `확인`은 누르지 않는다.
* 하루의 첫 접속에는 날짜 변경 알림, 타이틀, 출석부, 공지 팝업이 차례로 나온다. 스캔을 시작하기 전에 로비인지 확인해야 한다.

BAReceipt에는 화면에서 읽을 수 없는 값도 있다(소모한 AP, 크레딧, 청휘석, 선물 사용 횟수, 모집 티켓 사용 횟수). 이런 값은 스캔 대상이 아니고 사용자가 직접 입력한다.

## 이벤트 스테이지는 둘로 나눠 기록한다

지난 이벤트의 스테이지는 이벤트가 끝난 뒤에도 늘 열려 있어서 언제든 확인할 수 있다. 같은 이벤트가 나중에 복각되어 열릴 수도 있다. 이벤트가 실제로 열려 있는 동안의 기록과 상시 열린 지난 이벤트의 기록은 의미가 다르므로 섞지 않는다.

* `event.open`: 지금 열려 있는 이벤트의 스테이지 완료와 진행. 스캔한 시각과 이벤트 이름을 함께 남긴다.
* `event.past`: 상시 열린 지난 이벤트의 스테이지 완료와 진행.

같은 이벤트라도 열려 있는 동안 스캔했는지 끝난 뒤에 스캔했는지가 기록에 남아야 하므로, 항목마다 `scanned_while_open`을 둔다.

## 설계 원칙

* 클릭할 위치를 화면 좌표 상수로 박지 않는다. OCR로 읽은 글자 상자(예: "스토리", "이벤트")의 위치를 눌러서, 4:3과 16:9 어느 쪽에서도 같은 코드가 돌게 한다.
* 입력은 스캔에서만 보낸다. 안전장치와 ESC 중단은 학생 스캔과 같은 경로를 쓴다([ADR 0004](adr/0004-input-policy.md)).
* 읽은 값은 JSON으로 `%APPDATA%\baocr\progress\`에 쓰고, 읽을 때의 화면 비율과 시각을 함께 기록한다.
* 값이 불확실하면 비워 두고 이유를 남긴다. 추측해서 채우지 않는다.

## 진행 순서

1. 화면 조사. 각 값이 있는 화면을 기록하고 글자 위치와 읽는 법을 정한다.
2. 화면 종류를 `Scene`에 추가하고 분류 테스트를 만든다.
3. 값마다 읽는 함수와 고정 자료 테스트를 만든다.
4. 화면을 순회하는 스캔 모듈을 만든다. 순회 도중 중단해도 읽은 값은 남긴다.
5. BAReceipt 백업 파일 내보내기. 키 구조는 위 표와 같고, 각 키는 JSON 문자열이다.
6. 라이브 확인. 4:3과 16:9에서 모두 돌려 본다.

## 순수 로직 크레이트

`rust/crates/progress`(`baocr-progress`)가 게임과 OCR 엔진 없이 도는 읽기 로직과 내보내기를 가진다. 입력은 화면 하나의 글자 상자(`TextBox`)와 필요할 때 프레임이고, 읽지 못한 값은 `null`로 두고 `warnings`에 이유를 적는다. 위치는 글자 상자 사이의 상대 거리로 찾아서 두 화면 비율에서 같은 코드가 돈다. 화면 순회는 다른 모듈이 맡는다.

| 모듈 | 읽는 것 | 고정 자료 |
|---|---|---|
| `schema` | `ProgressSnapshot`과 하위 구조. 열린 이벤트(`events.open`)와 지난 이벤트(`events.past`)는 다른 구조이고 항목마다 `scanned_while_open`이 있다 | |
| `account` | 로비(모모톡 화면도 같음) 왼쪽 위의 `LV.`, 닉네임, 레벨 | `w169-lobby`, `w169-momotalk-list` |
| `schedule` | `RANK n` 줄과 오른쪽 지역명, `지역 랭크 총합` 옆의 합계. 보이는 줄만 돌려주고 합치는 일은 호출하는 쪽이 한다 | `w169-schedule` |
| `event_open` | `개최 기간` 줄, 스테이지 줄(번호, 이름, `입장`). 탭 종류는 호출하는 쪽이 알려 준다. 이름은 그림 로고라 항상 null | `w169-event-open`(+png), `w169-event-open-story` |
| `stars` | 번호 상자 아래 별 세 개 중 켜진 개수. 노란색과 회색 픽셀 수로 센다 | `w169-event-open.png`, `w169-mission-list.png` |
| `missions` | `제N임무`, Normal/Hard 탭(어두운 쪽이 선택됨), `19-2` 줄의 별 | `w169-mission-list`(+png) |
| `story` | 편 화면의 제목, `클리어` 표지, 장 목록. 장 화면의 `모든 에피소드를 클리어 했습니다.` | `w169-main-story`, `w169-main-chapter-cleared` |
| `event_past` | 이벤트 일람 격자. 카드 테두리의 긴 회색 선으로 칸을 나누고 칸마다 붉은 `complete!` 도장을 찾는다 | `w169-event-list-past.png`(9칸, 도장 8개) |
| `momotalk` | 모모톡 목록 줄. 분홍 하트를 색으로 찾고 같은 줄의 이름 상자와 묶는다 | `w169-momotalk-list`(+png) |
| `bareceipt` | 백업 파일 내보내기 | 단위 테스트 |

값이 없다는 것과 아직 모른다는 것을 구분하는 규칙이 몇 가지 있다.

* 장 화면에서 `모든 에피소드를 클리어` 문구가 없다고 `cleared: false`로 쓰지 않는다. OCR이 놓쳤을 수 있으므로 null로 두고 호출하는 쪽이 다시 읽은 뒤 정한다.
* 이벤트 스테이지의 별 아이콘이 보이지 않으면 0이 아니라 null이다. 스토리 탭의 줄은 별이 없으므로 항상 null이다.
* 모모톡의 인연 랭크 숫자는 OCR이 읽지 못한다(하트 안의 글자). 하트의 위치를 돌려주므로 호출하는 쪽이 잘라낸 그림을 `Ocr::line`으로 읽고 `parse_bond`에 넘긴다.

4:3 기록은 일정, 이벤트, 스토리 화면에 없다. 이 모듈들은 상자 높이에 대한 비율과 상대 위치만 쓰고 픽셀 상수를 쓰지 않지만, 4:3에서의 동작은 실제 기록으로 확인하지 못했다. 별 위치(번호 상자 높이의 0.44배 아래, 간격 0.56배)와 도장 크기(칸 높이의 0.18배 이상, 칸 오른쪽 40퍼센트)는 16:9에서 잰 값이다.

## BAReceipt 내보내기

BAReceipt의 "파일로 저장"은 JSON 객체 하나를 쓴다. 키는 `basic, students, fav, raid, grand, elim, main, event, mini, group, collab, gift, journal`이고, 값은 페이지가 localStorage에 둔 문자열을 그대로 담으므로 값 하나하나가 다시 JSON으로 인코딩된 문자열이다. "불러오기"는 파일에 있는 키만 localStorage에 덮어쓴다. 그래서 스캔이 모르는 키는 파일에서 아예 빼고, 사용자가 손으로 입력한 값을 그대로 둔다. 쓰는 키는 그 키의 값 전체를 바꾼다(`basic`을 쓰면 기본 정보의 다른 칸이 비워진다).

| 키 | 내용 | 출처 |
|---|---|---|
| `basic` | `in-nick`, `in-level`(문자열), `in-circle`(읽은 경우), `in-students`(학생 스캔 요약의 길이) | `account`와 학생 요약 |
| `students` | 학생 요약마다 `{name, skill, momo}`. `name`은 레벨과 성급을 아는 경우 `이름 (Lv. 90, 5성)`, 모르면 이름만. `skill`과 `momo`는 비운다 | 학생 요약 |
| `main` | 편 하나가 모두 클리어이면 `ms_N_ch`, `ms_N_ep`에 그 편의 전체 장과 화 수를 넣는다. 장별 상태를 다 알고 일부만 클리어이면 `ms_N_ch`에 클리어한 장 수만 넣는다. 여섯 번째 편의 키는 `ms_7`, Final은 `ms_6`이다(페이지 목록 순서) | `story` |
| `event` | 지난 이벤트 목록의 위치 i(0부터)가 클리어이면 `es_{i+1}`에 그 이벤트의 전체 화 수를 넣는다. 페이지 목록에서 순서가 게임 목록과 같다고 볼 수 있는 `es_1`부터 `es_27`까지만 대응한다 | `event_past` |

내보내지 않는 것은 다음과 같다.

* `fav, raid, grand, elim, mini, group, collab, gift, journal`: 스캔이 읽지 않는다.
* 열린 이벤트의 스테이지: 페이지에 대응하는 칸이 없다. 스냅샷 JSON에만 남는다.
* 모모톡 인연 랭크: 페이지의 `momo` 칸은 인연 랭크가 아니라 인연 스토리 에피소드 진행도(`EP n 완료`)라서 값이 다르다. 대응 규칙을 확인하기 전에는 넣지 않는다.
* 스케줄과 임무: 페이지의 입력 칸이 숫자 하나씩(`in-schedule`, `in-mission-normal` 등)이고 뜻이 스캔한 값과 같은지 확인하지 못했다.
* 학생 스킬: 학생 스캔 요약에 없다.

불확실한 점이 둘 있다. 페이지의 이벤트 목록과 게임 목록의 순서가 `es_27` 이후에는 맞지 않을 수 있어서 그 뒤의 지난 이벤트는 건너뛰고 경고를 남긴다. 그리고 `skill`이 빈 학생 항목을 페이지가 어떻게 그리는지는 실제 페이지에서 불러와 보지 못했다.

## 스캔 실행부

`rust/crates/cli/src/progress_scan.rs`가 화면을 돌며 위 읽기 함수를 부른다. 시작은 메뉴 카드의 `진행 상태 스캔` 버튼 또는 `baocr --scan-progress`이다. 입력 안전장치, ESC 중단, 입력 잠금은 학생 스캔과 같은 경로다.

* 누르는 곳은 `Target`에 적힌 라벨(로비의 스케줄, 이벤트 일람, 이벤트 스토리 탭)과 홈 아이콘뿐이다. 보상 받기, 입장, 확인은 목록에 없다.
* 이벤트 일람의 라벨은 OCR이 못 읽는 때가 많아서, 그 옆의 시계 글자(`AM7:32`)를 기준으로 아이콘 위치를 찾는다.
* 화면을 연 뒤 장면을 알아보지 못하면(전환 중) 세 번까지 다시 본다. 누른 뒤 화면이 안 바뀌면 한 번 더 누른다.
* 이벤트 일람은 마지막에 연 탭으로 열리므로 탭을 눌러도 화면이 안 바뀔 수 있다. 탭은 안 바뀌어도 실패로 보지 않는다.
* 목록은 휠로 내리고 얼마나 움직였는지를 화면에서 잰다(`scroll::content_shift`). 이벤트 카드의 번호는 움직인 거리의 합으로 매긴다. 같은 화면을 두 번 보고 한 번이라도 도장이 보이면 도장이 있는 것으로 센다(도장이 반짝여서 한 번만 보면 놓친다).
* 결과는 `%APPDATA%\baocr\progress\latest.json`과 시각이 붙은 사본, BAReceipt 백업 `bareceipt-backup.json`이다. 읽지 못한 구역은 비워 두고 `warnings`에 이유를 남긴다.

아직 스캔하지 않는 구역과 이유.

* 열린 이벤트의 스테이지. 이벤트 화면으로 들어가는 길이 로비 오른쪽 위의 돌아가는 배너뿐이라(몇 초마다 다른 배너로 바뀐다) 누르는 순간 어떤 배너인지 보장되지 않는다. 읽는 함수는 있다.
* 메인 스토리. 한 화면에 한 편씩 보이고 1부/2부/3부 전환과 편 선택이 따로 있다. 화면 기록은 있으나 순회를 만들지 않았다.
* 임무 별, 모모톡, 미니·그룹 스토리, 서클.

### 메인 스토리 구역의 현재 상태

볼륨 지도(1부/2부)를 휠로 훑고 카드의 `클리어`/`New` 표지를 읽는다. 읽는 함수(`parse_volume_cards`)는 4:3과 16:9 기록으로 테스트한다. 순회는 불안정하다. 같은 코드가 한 번은 두 화면비에서 모든 볼륨을 읽었고, 다음 실행에서는 "부 전환 버튼을 찾지 못했습니다"로 비웠다. 선택된 카드는 표지가 가려지고 고정 대기 시간에 기대는 탓으로 보이며, 원인은 확인하지 못했다. 실패하면 이 구역만 비고 `warnings`에 남는다. 안정화하기 전에는 이 구역의 값을 믿지 않는다.

## 설계 결정: 스토리와 이벤트 (2026-11-24)

* **스토리 목록은 DB가 가진다.** 편, 장, 에피소드 수 같은 고정 정보는 정적 데이터(`wiki.db`)로 관리한다. 스캔은 화면에서 목록을 알아내지 않고, 사용자별 클리어 지표만 기록한다.
* **편 카드의 클리어 표지만 읽지 않는다.** 장 단위로 표지를 확인하고, DB 목록 기준으로 끝까지 진행한 이력이 확인되면 그 장의 모든 에피소드를 클리어로 친다.
* **열린 이벤트는 배너를 직접 고른다.** 로비의 돌아가는 배너를 돌려 가며 모든 배너를 하나씩 인식하고, 이벤트 배너일 때 그것을 연다. 누르는 순간 어떤 배너인지 보장되지 않는 문제는 이 방식으로 푼다.
* 이 결정에 따라 지금의 메인 스토리 볼륨 지도 순회(`main_story_section`)는 대체 대상이다.

목록의 출처는 [arisu-archive/bluearchive-data](https://github.com/arisu-archive/bluearchive-data)의 `global` 브랜치다(게임 클라이언트 테이블을 푼 JSON). 그 저장소에는 LICENSE 파일이 없고 데이터는 게임사 것이므로 서브모듈로 넣거나 원본을 이 저장소에 두지 않는다. DB 수집기(`wikidb`)가 `ScenarioModeExcel`, `EventContentSeasonExcel`, `EventContentScenarioExcel` 세 표를 그 시점의 커밋에서 내려받아 숫자(번호, 개최·종료 시각)만 `wiki.db`의 `story_episode`, `event`, `event_scenario`에 넣고 커밋 해시를 `source.version`에 남긴다. DB 파일은 배포하지 않는다. 이 표의 `mode_type`, `sub_type` 값이 메인, 미니, 그룹 중 무엇인지는 아직 풀지 않았다.
