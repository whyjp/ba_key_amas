# 스캔 속도와 OCR 진단

2026-11-25에 한 진단이다. 게임에 입력을 보내지 않고 기존 기록(`input.log`, 스캔 결과 파일), 커밋된 픽스처, 연구 폴더의 TrOCR 자료만 썼다.

## 1. 학생 스캔 시간 (상세 포함, 106명)

사용자의 실제 스캔 기록에서 잰 값이다. 학생마다 `student.json`을 쓴 시각의 간격이다.

| 항목 | 값 |
|---|---|
| 총 시간 | 1075 s (약 18분) |
| 학생당 | 중앙값 10.23 s, 평균 10.24 s, 최대 11.32 s |
| 학생당 입력 | 클릭 6회와 스크롤 2회 (`input.log`) |
| 클릭 한 번 | 중앙값 734 ms (최소 514, 최대 790) |
| 스크롤 한 번 | 약 0.85 ~ 1.27 s |
| 입력 사이 간격 | 중앙값 1.11 s |

**원인.** 클릭 한 번이 734 ms 걸리는 이유는 `hcu/src/native.rs`의 `wait_still`이다. 입력 뒤에 창이 두 번 연속 픽셀까지 같을 때까지 기다리는데, 게임은 움직이는 배경 때문에 그런 순간이 없어서 항상 상한(600 ms)까지 기다린다. 그런데 스캔 쪽 호출부(`deep::settle`, `deep::settle_quiet`, `wait_stable_next`, 진행 상태 스캔의 `settle`)는 모두 화면이 바뀐 뒤 안정될 때까지 스스로 기다린다. 그래서 이 600 ms는 중복이다.

**고침(`scan-speed` 브랜치).** 클릭 뒤 대기를 기본 0으로 했다. 스크롤 뒤 대기(600 ms)는 그대로다. 팝업 맨 위와 맨 아래를 읽는 단계가 이 대기에 기대고 있어서, 라이브로 확인하기 전에는 건드리지 않았다. `BAOCR_HCU_CLICK_SETTLE_MS=600`으로 예전 동작으로 돌릴 수 있다.

**기대.** 학생당 클릭 6회 × 약 0.6 s = 약 3.6 s를 줄인다. 10.2 s가 약 6.6 s가 되고, 106명은 약 18분에서 약 11.5분이 된다(예측이다. 라이브 측정은 못 했다).

**확인 방법.** 학생 목록에서 상세 포함 스캔을 한 번 돌린 뒤 다음을 실행한다. 이전 스캔은 `D:\scan-run\baseline-scan-20261125`에 보관했다.

```
python scripts/compare_scans.py D:\scan-run\baseline-scan-20261125\students.json %APPDATA%\baocr\students\students.json ^
  --details-old D:\scan-run\baseline-scan-20261125\details --details-new %APPDATA%\baocr\students\details
```

읽은 값이 하나라도 다르면 학생별로 필드를 보여 준다. 같으면 속도만 달라진 것이다.

**남은 지점.** `settle`과 `settle_quiet`은 확인 사이에 100 ms씩 쉰다. 60 ms로 줄이면 학생당 1 s 안팎을 더 줄일 수 있을 것으로 추정하지만, 측정하지 않았다. 스크롤 뒤 대기를 250 ms로 줄이는 것도 같다.

## 2. 이름판 OCR (진행 상태 스캔의 듀티 목록)

`ba-key-AMAS --eval-plates scanner/fixtures/plates`로 160장을 다시 쟀다(CPU).

| 방식 | 정확히 일치 | 장당 시간 |
|---|---|---|
| 검출기만 | 152/160 | 16 ms |
| 스캔의 판독 경로(2x, 3x, 4x 재판독) | 155/160 | 83 ms |

틀린 5장은 슌을 순으로, 아야네를 아네로, `이즈미(새해)`의 닫는 괄호 누락, 츠루기를 초루기로 읽은 것이다. 모두 사전에 맞춰 보정하는 단계(`snap`)가 고치는 종류의 오류다. 이 측정은 보정 전 원시 판독이다. 그러므로 이름판 쪽은 정확도 병목이 아니다. 사용자의 실제 스캔에서도 106명 모두 이름이 `exact`로 맞았고 중복이 없었다.

## 3. TrOCR (`trocr` 브랜치, main에 병합됨)

같은 160장 기준으로 연구 쪽 수치는 160/160이다. Rust 이식은 입력이 참조와 비트 단위로 같고 정답이 1위인 경우가 30/30이었다(10장 × 3조건). 장당 시간은 후보 수에 달렸다.

| 후보 | 전처리 | 인코더 | 점수화 | 합계 |
|---|---|---|---|---|
| 280명 전체 | 12 ms | 109 ms | 794 ms | 약 915 ms |
| 24명 | 5 ms | 98 ms | 66 ms | 약 170 ms |
| 8명 | 8 ms | 98 ms | 26 ms | 약 130 ms |

다른 독해기가 후보를 8 ~ 24명으로 줄여 주면 TrOCR이 130 ~ 170 ms에 검증할 수 있다. 다만 이름판의 원시 오류가 보정 단계에서 이미 고쳐지므로, 지금은 연결해도 얻는 정확도가 없다. 라이브 빠른 편성 이름 읽기에는 느리다(18장 × 130 ms). 초상화 인식이 그 자리를 이미 채운다.

**결론.** 정확도 쪽은 현재 측정에서 손볼 곳이 없다. TrOCR은 흐린 화면이나 새 해상도처럼 원시 판독이 무너지는 경우를 위한 예비로 두고, 속도는 1절의 대기 제거에서 얻는다.
